# Dataset Plan & Sourcing
**Project**: AIOps Sentinel – Self-Healing Cloud Platform  
**Phase**: Phase 3 (ML Engineering Design)  

Since machine learning models suffer from the "Cold Start" problem (lack of initial historical data on a brand-new platform), we will bootstrap the ML modules using publicly available, high-quality AIOps datasets. As the platform generates internal telemetry over time, we will transition to fine-tuning on our proprietary data.

---

## 1. Anomaly Detection
### Public Dataset Sourcing
- **Numenta Anomaly Benchmark (NAB)**: A comprehensive collection of streaming time-series data with labeled anomalous periods.
  - *Usage*: Train the LSTM-Autoencoder or Isolation Forest to recognize structural spikes, contextual anomalies, and noise.
- **Yahoo S5 Webscope Dataset**: Contains real and synthetic time-series data related to web traffic and CPU utilization with labeled anomalies.
  - *Usage*: Excellent for establishing baseline metrics models.

### Internal Data Transition
- **Data Source**: `Metric` table.
- **Trigger**: Once we accumulate > 30 days of continuous CPU/Memory telemetry generated by `app/data_seed.py`, we will trigger a re-training pipeline.

---

## 2. Alert Clustering & NLP
### Public Dataset Sourcing
- **Loghub / HDFS Log Dataset**: A massive corpus of labeled system logs and alerts.
  - *Usage*: Pre-train the BERT model (Masked Language Modeling) to understand system terminology (e.g., "OOM", "Connection Refused", "Timeout") before doing HDBSCAN clustering.
- **Alibaba Cluster Trace Program**: Open-source traces of millions of tasks and alerts.

### Internal Data Transition
- **Data Source**: `Alert` and `Log` tables.
- **Trigger**: Continuous batch processing. Every week, new alert signatures are vectorized and added to the HDBSCAN training pool.

---

## 3. Root Cause Analysis
### Public Dataset Sourcing
- **AIOps Challenge Datasets (e.g., CCF AIOps)**: Provide exact microservice topology graphs along with metric anomalies and the ground-truth "root cause" service.
  - *Usage*: Essential for training the Graph Convolutional Network (GCN) to understand how errors propagate upstream and downstream.

### Internal Data Transition
- **Data Source**: `Incident` table (`resolvedAt`, `rootCauseService` tags if added manually by operators).
- **Trigger**: Requires human-in-the-loop (SREs). Once operators resolve 100+ incidents and tag the root cause node, the graph model can be fine-tuned.

---

## 4. Risk Prediction (Deployments)
### Public Dataset Sourcing
- **Google DORA Metrics (Synthetic Extraction)**: While raw deployment datasets are rare (as they contain proprietary source code info), we can utilize open-source CI/CD failure datasets from GitHub Actions or TravisTorrent.
  - *Usage*: Extract features like commit size, language, and author experience to predict build/deployment failures.

### Internal Data Transition
- **Data Source**: `Deployment` table joined with `RiskScore`.
- **Trigger**: As deployments transition status from `PENDING` -> `SUCCESS` or `ROLLED_BACK`, we auto-generate labeled rows. Requires ~500 deployments to train a robust XGBoost classifier.

---

## 5. RAG / Vector Database Context
### Public Dataset Sourcing
- **Kubernetes Official Documentation**: Scraped Markdown files from `kubernetes.io`.
- **Open-Source Runbooks**: e.g., GitLab's public runbooks (`gitlab.com/gitlab-com/runbooks`).
  - *Usage*: Seed the Vector DB (Qdrant/Milvus) so the RAG model can answer infrastructure queries immediately without needing internal playbooks to be authored first.

### Internal Data Transition
- **Data Source**: `Playbook` table.
- **Trigger**: Every time an internal playbook is created or updated, a background worker will chunk the text, generate embeddings, and upsert them into the Vector Database.
